# Управление базой знаний F-Engineering

Статус: `Approved`

## Назначение

Этот документ задает порядок работы с базой знаний `f-engineering-knowledge-base`.

Главная цель — разделить:

- общие правила, которые действуют всегда;
- стандарты оформления результата;
- методики конкретных видов работ;
- шаблоны;
- экспериментальные предложения.

Так агент не должен применять всю библиотеку сразу. Для каждой задачи он собирает нужный набор правил по карте применения.

## Уровни правил

| Уровень | Что содержит | Когда применять |
|---|---|---|
| Core | общая организация работы, проектные папки, версии, запреты на перенос клиентских материалов в GitHub | всегда |
| Style | оформление результата: HTML, PDF, презентации, таблицы, фирменная палитра | когда выбран формат результата |
| Workflow | методика выполнения конкретного вида работы | когда задача относится к этому типу работ |
| Template | заготовка документа или структуры | когда нужен быстрый старт |
| Proposal | новое или экспериментальное правило | только по прямому указанию пользователя или в пилотной задаче |

## Приоритет при конфликте

Если правила противоречат друг другу, применять такой порядок:

1. Системные ограничения безопасности и приватности.
2. `AGENTS.md` конкретной рабочей папки проекта.
3. Утвержденные правила из ветки `main`.
4. Методика конкретного вида работы.
5. Стандарт оформления выбранного выходного формата.
6. Шаблон.
7. Предложения и экспериментальные ветки.

Более конкретное утвержденное правило имеет приоритет над более общим правилом.

Пример: методика фасадного аудита определяет состав проверяемых фасадных категорий, а HTML-стандарт определяет мобильную верстку и способ встраивания проверочных превью.

## Статусы знаний

| Статус | Значение | Можно применять автоматически |
|---|---|---|
| Draft | черновая идея | нет |
| Candidate | сформулировано, но не проверено на достаточном числе задач | нет, кроме пилота |
| Pilot | проверяется на одном или нескольких проектах | только для указанного проекта |
| Approved | принято в `main` и действует | да |
| Deprecated | правило устарело | нет |

## Как добавлять новое знание

1. Не записывать новое универсальное правило напрямую в действующий стандарт.
2. Сначала создать предложение в `proposals/` или отдельную ветку.
3. Указать:
   - причину появления;
   - из какого кейса правило возникло;
   - область применения;
   - ограничения;
   - критерии готовности;
   - какие существующие правила оно дополняет.
4. Проверить на реальной задаче.
5. После подтверждения пользователем перевести в `Approved`.
6. Обновить:
   - `registry/KNOWLEDGE_REGISTRY.md`;
   - `registry/APPLICATION_MAP.md`;
   - при необходимости `registry/BRANCH_REGISTRY.md` и `registry/RULE_CONFLICTS.md`.

## Как применять знания в новом проекте

1. Открыть `START_HERE.md`.
2. Открыть `AGENTS.md`.
3. Открыть `registry/KNOWLEDGE_REGISTRY.md`.
4. Найти тип задачи в `registry/APPLICATION_MAP.md`.
5. Прочитать только те методики и стандарты, которые указаны для задачи.
6. Если задача новая и подходящего workflow нет, использовать core + нужный style, а новое знание оформить как предложение.

## Что не хранить в GitHub

В GitHub нельзя переносить:

- клиентские исходники;
- проектные PDF, DWG, XLSX, DOCX;
- финансовые данные;
- персональные и коммерческие материалы;
- большие рабочие артефакты, не являющиеся универсальным правилом.

В GitHub попадают только обезличенные правила, стандарты, шаблоны и предложения.

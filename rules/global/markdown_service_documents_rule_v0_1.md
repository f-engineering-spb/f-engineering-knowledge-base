# F-engineering · правило служебных Markdown-документов

**Версия:** 0.1  
**Статус:** принято как рабочее правило  
**Контур:** F-engineering Knowledge Library / GitHub Knowledge Base  
**Область применения:** промежуточные служебные документы, архитектурные заметки, правила, сценарии, модули, рабочие рассуждения с ассистентом

---

> [!IMPORTANT]
> **Главное правило:** все служебные документы, которые рождаются в рабочем диалоге с ассистентом, по умолчанию оформляются в Markdown.

---

## 1. Почему Markdown становится базовым форматом

Markdown выбран как основной формат для служебных документов F-engineering, потому что он хорошо читается в трёх рабочих средах:

| Среда | Почему удобно |
|---|---|
| **Телефон** | текст читается спокойно, блоки не разваливаются, внимание держится на смысле |
| **VS Code** | машинный шрифт, спокойная структура, удобная навигация по заголовкам |
| **GitHub** | версионность, история изменений, простое хранение в базе знаний |

> [!NOTE]
> Markdown не пытается быть “красивым офисным документом”. Он работает как чистый инженерный текст: быстро открыть, быстро прочитать, быстро поправить, быстро закоммитить.

---

## 2. Базовая философия

Служебный документ должен быть ближе к VS Code, чем к Word.

Он должен давать ощущение:

```text
минимум оформления
максимум смысла
машинная чистота
понятная структура
никакой визуальной пены
```

> [!TIP]
> Если документ нужен для размышления, постановки задачи, описания модуля, архитектуры, правил или промежуточной фиксации решения — это Markdown.

---

## 3. Что делаем только в Markdown

По умолчанию в Markdown оформляются:

- архитектурные решения;
- правила работы;
- спецификации модулей;
- дорожные карты;
- промежуточные выводы из диалогов;
- инструкции для ассистентов и агентов;
- описания сценариев;
- логика интерфейсов;
- проектные гипотезы;
- чек-листы;
- решения “принято / не принято”;
- рабочие резюме после обсуждений.

> [!IMPORTANT]
> Если документ нужен нам для мышления, разработки или фиксации правил, он должен быть Markdown-файлом.

---

## 4. Когда HTML всё-таки допустим

HTML не используется для промежуточных служебных документов.

HTML допустим только когда нужен:

- демонстрационный макет интерфейса;
- интерактивный просмотрщик;
- визуальная витрина для отправки вовне;
- отчёт, который должен открываться в браузере;
- документ с кастомной вёрсткой, которую Markdown не поддерживает.

> [!WARNING]
> HTML не должен подменять Markdown в рабочем контуре. HTML — это витрина. Markdown — это рабочая тетрадь машины и человека.

---

## 5. Когда нужен DOCX / PDF

DOCX и PDF используются не для мышления, а для передачи наружу.

| Формат | Когда использовать |
|---|---|
| **DOCX** | официальное письмо, договорный документ, документ для правок внешним пользователем |
| **PDF** | финальная выдача, отправка заказчику, фиксация версии |
| **HTML** | браузерная витрина, интерфейс, навигатор |
| **Markdown** | рабочая фиксация, правила, архитектура, инструкции, модули |

---

## 6. Визуальный стиль Markdown

Markdown-документы должны быть не сухой простынёй, а структурным инженерным текстом.

Используем:

- заголовки `#`, `##`, `###`;
- короткие абзацы;
- таблицы;
- кодовые блоки для схем;
- callout-блоки;
- списки только там, где они реально помогают;
- выделение ключевых формул;
- служебные “цветные выпучки” через GitHub/Obsidian callouts.

---

## 7. Цветные callout-блоки

Используем стандартные callout-блоки:

```markdown
> [!NOTE]
> Нейтральное пояснение.

> [!TIP]
> Практическая рекомендация.

> [!IMPORTANT]
> Ключевое правило или архитектурное решение.

> [!WARNING]
> Риск, ограничение, место, где легко ошибиться.

> [!CAUTION]
> Запрет или опасное действие.
```

### Семантика callout-блоков

| Блок | Назначение |
|---|---|
| `NOTE` | пояснение, контекст, спокойная справка |
| `TIP` | рекомендация, удобный приём, рабочий совет |
| `IMPORTANT` | принятое правило, главный вывод, архитектурная ось |
| `WARNING` | риск, спорное место, возможная ошибка |
| `CAUTION` | запрет, опасное действие, не делать |

> [!CAUTION]
> Не использовать callout-блоки как украшение. Каждый цветной блок должен нести смысловую нагрузку.


## 9. Именование файлов

Файлы называются латиницей, спокойно и предсказуемо.

Формат:

```text
<area>_<topic>_v0_1.md
```

Примеры:

```text
fero_assistant_launcher_logic_commercial_v0_1.md
markdown_service_documents_rule_v0_1.md
project_state_spec_v0_1.md
module_spec_BPM-001_v0_1.md
```

> [!TIP]
> В имени файла лучше использовать смысл, чем красивость. Файл должен находиться глазами и поиском.

## 12. Практическое правило для ассистента

При создании промежуточных служебных документов ассистент должен по умолчанию:

1. создавать Markdown-файл;
2. использовать callout-блоки для смысловых акцентов;
3. не создавать HTML-дубль без отдельной просьбы;
4. не превращать служебный документ в офисную презентацию;
5. держать стиль ближе к VS Code / GitHub, чем к Word;
6. сохранять машинную читаемость текста;
7. использовать HTML только для макетов интерфейсов, навигаторов и внешних витрин.

> [!NOTE]
> Если пользователь просит “красиво прочитать”, сначала предлагать Markdown. HTML делать только если нужна браузерная демонстрация или интерактивная вёрстка.

---

## 13. Принятое решение

С этого момента для рабочего контура F-engineering действует правило:

```text
Все служебные документы, возникающие в работе с ассистентом,
по умолчанию создаются в Markdown.
HTML не создаётся автоматически.
```

Исключения возможны только по прямой просьбе пользователя или когда сама задача требует HTML: просмотрщик, интерфейс, навигатор, макет, браузерная витрина.

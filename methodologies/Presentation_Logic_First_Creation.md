# Методика создания презентаций через согласование логики

Статус: `Candidate`

## Назначение

Методика применяется, когда нужно создать презентацию, в которой важна не только
визуальная подача, но и точная управленческая, техническая или коммерческая
аргументация.

Главный принцип: **сначала строится логика презентации, затем создается HTML,
PPTX или другой визуальный документ**.

Эта методика появилась после сравнения двух подходов:

- прежний подход: большой массив вводных сразу превращался в HTML, а смысл
  уточнялся уже после появления документа;
- эталонный подход: главный тезис, блоки, функции слайдов и текстовая схема
  согласовывались до визуальной сборки.

## Когда применять

Применять методику, если задача содержит признаки:

- пользователь говорит о презентации, питче, предложении, модели взаимодействия,
  кейсе, услуге или возможностях F-Engineering;
- материал содержит несколько конкурирующих акцентов;
- пользователь проговаривает смысл голосом, а агент должен превратить его в
  слайды;
- есть риск преждевременно уйти в дизайн, кейсы, картинки или технические детали;
- презентация должна стать эталонной или повторяемой логикой для других
  проектов.

Не применять как основной порядок, если задача простая: например, нужно только
переверстать уже утвержденный текст или сделать экспорт существующей презентации.

## Главный запрет

Для сложной смысловой презентации **нельзя сразу делать HTML/PPTX из большого
потока вводных**.

Сначала необходимо согласовать:

1. главный тезис;
2. блоки презентации;
3. роль каждого блока;
4. функцию каждого слайда;
5. ключевой текст слайда;
6. текстовую блок-схему сверху вниз.

Только после этого выполняется визуальная сборка.

## Эталонный порядок работы

```text
1. Выявить главный тезис презентации.
2. Проверить, не слишком ли он узкий и не смещает ли акцент.
3. Согласовать формулировку первого слайда.
4. Разложить презентацию на 2-4 смысловых блока.
5. Для каждого блока определить:
   - что он раскрывает;
   - что он не должен подменять;
   - почему он стоит именно в этом месте.
6. Двигаться пошагово: один пункт или один слайд за раз.
7. После каждого спорного тезиса предлагать варианты формулировок.
8. Фиксировать тезис только после подтверждения пользователя.
9. Нарисовать всю презентацию текстовыми блоками сверху вниз.
10. Согласовать визуальную логику слайдов.
11. Только после этого собрать HTML/PPTX.
12. Проверить результат браузером/скриншотами/мобильной шириной.
13. Сообщить пользователю, где лежит файл и что проверено.
```

Короткая формула:

```text
Тезис -> блоки -> функция слайда -> текстовая схема -> визуальная схема -> HTML/PPTX
```

Неправильная формула:

```text
Материалы -> дизайн -> правки -> поиск смысла
```

## Роли агента

В такой задаче агент работает не как дизайнер слайдов, а как набор
последовательных функциональных ролей.

### 1. Агент смысловой рамки

Задача: найти главный тезис и не дать презентации распасться на набор важных, но
несвязанных мыслей.

Проверочные вопросы:

- что мы на самом деле предлагаем;
- что является главным акцентом;
- что является вспомогательным блоком;
- какие темы нельзя сделать центром презентации.

### 2. Агент структуры

Задача: разложить тезис на блоки и определить порядок раскрытия.

Выход:

```text
Блок 1. Вводный тезис
Блок 2. Техническая часть
Блок 3. Экономическая / управленческая часть
Блок 4. Релевантный опыт / иллюстрация
```

Названия блоков всегда зависят от конкретной презентации.

### 3. Агент редактора формулировок

Задача: превращать устную речь пользователя в слайдовый текст без потери
смысла.

Правила:

- предлагать 2-4 варианта, если формулировка еще не созрела;
- не фиксировать спорную формулировку без подтверждения пользователя;
- сохранять слова пользователя, если они точнее агентской редакции;
- устранять повторы между соседними слайдами.

### 4. Агент блок-схемы

Задача: до визуальной сборки показать всю презентацию текстовыми блоками.

Формат:

```text
БЛОК 1. НАЗВАНИЕ
┌──────────────────────────────────────────────┐
│ Слайд 1                                      │
│ Заголовок                                    │
│                                              │
│ Ключевой текст                               │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Слайд 2                                      │
│ ...                                          │
└──────────────────────────────────────────────┘
```

Не заменять этот этап Mermaid-диаграммой, если пользователь просит увидеть
слайды как текстовые квадраты сверху вниз.

### 5. Агент визуальной схемы

Задача: перед HTML/PPTX описать, как каждый слайд будет визуализирован.

Для каждого слайда указать:

- тип визуала: титул, две колонки, матрица, процесс, временная линия, таблица,
  фото-кейс;
- нужны ли изображения;
- какие изображения допустимы;
- что не должно отвлекать от тезиса.

### 6. Агент сборки

Задача: собрать документ строго по утвержденной логике.

Правила:

- не добавлять новые смысловые блоки без согласования;
- не менять утвержденные формулировки ради дизайна;
- сохранять статусную версию файла;
- для HTML соблюдать `document-standards/HTML_Mobile_Standard.md`;
- проверять мобильную ширину и отсутствие горизонтального overflow.

## Как работать с кейсами и изображениями

Кейс или объект не должен автоматически становиться доказательством опыта.
Сначала определить его роль:

- иллюстрация похожей логики;
- подтверждение прохождения похожего процесса;
- визуальная привязка;
- технический пример;
- доказательный материал.

Если роль кейса нейтральная, нельзя писать его как портфолио или как главный
аргумент.

Клиентские изображения, PDF, DWG, XLSX и проектные материалы не переносить в
GitHub. В методику можно переносить только обезличенное описание подхода.

## Как вызывать эту методику в чате

Пользователь может написать:

- `Создай презентацию по логико-первой методике`;
- `Работай как агент создания презентаций`;
- `Сначала согласуем логику презентации, потом делай HTML`;
- `Сделай презентацию по эталонной схеме: тезис, блоки, слайды, текстовая схема, визуализация`;
- `Не делай сразу HTML, сначала нарисуй блок-схему слайдов сверху вниз`.

После такой команды агент должен:

1. прочитать эту методику;
2. спросить или вывести главный тезис;
3. работать пошагово по одному пункту или слайду;
4. не переходить к HTML/PPTX до утверждения блок-схемы.

## Мини-шаблон запуска

```text
Задача: создать презентацию.
Применить методику Presentation_Logic_First_Creation.
Не собирать HTML/PPTX сразу.
Сначала:
1. предложи главный тезис;
2. разложи презентацию на блоки;
3. согласуй каждый слайд пошагово;
4. нарисуй текстовую блок-схему сверху вниз;
5. предложи визуализацию;
6. только после утверждения собери документ.
```

## Проверки перед выдачей

Перед финальным ответом агент должен проверить:

- у презентации есть главный тезис;
- каждый слайд имеет функцию;
- нет повторов между соседними слайдами;
- вспомогательные блоки не стали главным акцентом;
- кейсы и изображения выполняют заранее определенную роль;
- HTML не имеет горизонтального overflow на мобильном экране;
- кириллица читается корректно;
- клиентские материалы не перенесены в GitHub.

# Синхронизация и восстановление состояния Codex Desktop

Статус: `Candidate`

## Назначение

Инструкция определяет порядок сохранения, переноса и восстановления пользовательского состояния Codex Desktop при работе на нескольких компьютерах и после переустановки или сбоя приложения.

Под состоянием Codex Desktop понимаются:

- проекты и их порядок в левой панели;
- чаты и привязка каждого чата к рабочей папке проекта;
- закреплённые и архивированные чаты;
- вложения и сохранённые ссылки на файлы;
- настройки, правила, навыки, памяти и автоматизации Codex.

Проектные документы, исходные материалы и результаты работ хранятся по действующим правилам проектного хранилища. Настоящая инструкция относится только к пользовательскому состоянию Codex Desktop.

## Архитектура хранения

Используются три независимых уровня:

1. **Проектное хранилище** — рабочие папки, документы и результаты проектов.
2. **GitHub-база знаний** — инструкции, стандарты, методики и обезличенные инструменты.
3. **Облачное хранилище состояния Codex Desktop** — резервные снимки боковой панели, чатов, привязок и вложений.

Рабочую папку `%USERPROFILE%\.codex` запрещено напрямую синхронизировать средствами Google Drive, OneDrive или аналогичного клиента. В ней находятся изменяемые SQLite-базы; одновременная запись с нескольких компьютеров может повредить данные.

## Состав переносимого состояния

В резервный снимок включаются:

```text
sessions/
archived_sessions/
attachments/
automations/
memories/
rules/
skills/
generated_images/
.codex-global-state.json
session_index.jsonl
history.jsonl
config.toml
state_5.sqlite
goals_1.sqlite
memories_1.sqlite
```

В снимок не включаются:

- `auth.json`, токены, пароли и другие секреты;
- логи, кэши, временные файлы;
- браузерные профили и авторизационные данные;
- проектные документы, уже находящиеся в проектном хранилище.

SQLite-базы необходимо копировать согласованным способом через SQLite backup API либо после полного завершения Codex Desktop и Codex CLI.

## Структура облачного хранилища

```text
Codex_Desktop_State/
├── canonical/       # объединённое эталонное состояние
├── snapshots/       # датированные полные снимки
├── machines/        # исходные снимки отдельных компьютеров
├── manifests/       # читаемый реестр проектов и чатов
├── recovery-tools/  # инструменты Publish, Sync, Restore, Status
└── logs/            # журналы автоматического резервирования
```

`canonical` является источником для синхронизации и оперативного восстановления. `snapshots` используются для возврата к предыдущему состоянию. В `machines` сохраняется исходное состояние каждого компьютера перед объединением.

## Операции

### Publish

Выполняется после завершения работы и автоматически по расписанию.

Операция должна:

1. создать согласованный снимок локального состояния;
2. сохранить его в `machines/<computer>/<timestamp>`;
3. объединить новые уникальные чаты и проекты с `canonical`;
4. создать датированный полный снимок;
5. обновить читаемый манифест проектов и чатов;
6. записать результат в журнал.

### Sync

Выполняется перед началом работы на другом компьютере.

Операция добавляет из `canonical` отсутствующие проекты, чаты, вложения и настройки в локальное состояние. Перед синхронизацией рекомендуется завершить Codex Desktop. После синхронизации необходимо проверить левую панель и доступность рабочих папок.

### Restore

Используется после сбоя, переустановки или потери боковой панели.

Перед восстановлением Codex Desktop и Codex CLI должны быть полностью закрыты. Операция должна:

1. создать страховочную копию текущего локального состояния;
2. восстановить выбранный снимок или `canonical`;
3. вернуть проекты, чаты, привязки, вложения и настройки;
4. проверить целостность SQLite-баз;
5. проверить количество проектов и чатов по манифесту;
6. запустить Codex и визуально проверить левую панель.

### Status

Показывает расположение локального и облачного состояния, дату последнего снимка, количество проектов и количество чатов.

## Работа на нескольких компьютерах

Обязательный порядок:

1. Перед началом работы выполнить `Sync`.
2. Работать с проектами и чатами.
3. После завершения работы выполнить `Publish`.
4. Не продолжать один и тот же чат одновременно на двух компьютерах.
5. Использовать одинаковые пути к общим проектным папкам на всех компьютерах либо применять явное сопоставление путей.

Чаты имеют уникальные идентификаторы, поэтому новые независимые чаты можно объединять. Одновременное продолжение одного чата на двух компьютерах создаёт конфликт истории и не допускается.

## Автоматическое резервирование

На каждом рабочем компьютере должна быть настроена ежедневная задача `Publish` с запуском при первой возможности после пропущенного расписания. Дополнительно `Publish` выполняется вручную:

- перед обновлением или переустановкой Codex Desktop;
- перед значимыми изменениями настроек;
- после завершения важного проекта или длинного чата;
- перед переходом на другой компьютер.

## Проверка снимка

Каждый снимок считается пригодным только после проверки:

- `PRAGMA integrity_check` для SQLite-баз возвращает `ok`;
- количество чатов в базе соответствует манифесту;
- активные и архивированные сессии присутствуют;
- список проектов и привязки `чат → рабочая папка` присутствуют;
- вложения доступны;
- секреты и авторизационные данные отсутствуют.

Необходимо периодически выполнять тестовое восстановление в отдельную папку, не затрагивая рабочее состояние Codex.

## Действия после аварии

1. Не создавать новые проекты и чаты до восстановления.
2. Сохранить остатки локальной папки `.codex` отдельным аварийным снимком.
3. Переустановить Codex Desktop при необходимости.
4. Полностью закрыть Codex.
5. Выполнить `Restore` из последнего исправного снимка.
6. Проверить целостность баз, манифест и левую панель.
7. Только после проверки продолжать работу и выполнять новый `Publish`.

## Ограничения

- Система сохраняет локальные чаты Codex Desktop, но не заменяет резервирование проектных файлов.
- Ссылки на документы восстановятся, только если соответствующие файлы доступны по прежним путям либо пути корректно сопоставлены.
- Конфликты одновременного редактирования одного чата автоматически безопасно не объединяются.
- Авторизационные данные намеренно не переносятся; на новом компьютере необходимо войти в сервисы отдельно.

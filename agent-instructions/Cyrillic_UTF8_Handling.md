# Кириллица и UTF-8 для AI-агентов

Статус: `Approved`

## Назначение

Это правило применяется каждый раз, когда агент работает с русским текстом,
кириллическими именами файлов или папок, Markdown, HTML, CSV, JSON, TXT,
DOCX/XLSX-экспортами, PowerShell, GitHub, Google Drive, локальным диском или
любыми инструментами, которые могут исказить кодировку.

Цель — не допускать mojibake вида `РџСЂРёРІРµС‚`, не принимать битый вывод за
содержательный текст и не перезаписывать нормальную кириллицу испорченной
кодировкой.

## Главный принцип

Русский текст считать UTF-8, пока явно не доказано обратное.

Если кириллица отображается как `Рџ`, `Рґ`, `Рё`, `СЃ`, `вЂ”`, `â`, `Ð` или
похожая последовательность, это не текст для анализа, а ошибка кодировки.
Агент обязан остановить использование такого вывода и перечитать источник с
явным указанием кодировки.

## Обязательный алгоритм перед чтением русских файлов

1. Определить, что файл или путь содержит русский текст либо кириллицу.
2. Перед чтением локальных текстовых файлов на Windows включить UTF-8 вывод.
3. Читать файл с явным `UTF8`, а не полагаться на кодировку консоли по умолчанию.
4. Визуально проверить первые строки: русский текст должен выглядеть как русский.
5. Если виден mojibake, не делать выводов по этому тексту и не копировать его в
   новые файлы.
6. Перечитать файл другим способом: через `Get-Content -Encoding UTF8`, Python с
   `encoding="utf-8"`, GitHub connector, Google Drive connector или другой
   источник, который возвращает Unicode.
7. Только после нормального отображения использовать текст для анализа,
   резюме, правок и цитирования.

## PowerShell на Windows

Перед чтением русских файлов выполнять:

```powershell
[Console]::OutputEncoding = [Text.UTF8Encoding]::UTF8
Get-Content -LiteralPath '<path>' -Encoding UTF8 -Raw
```

Для записи русских текстовых файлов использовать UTF-8 без зависимости от
локальной ANSI-кодировки:

```powershell
Set-Content -LiteralPath '<path>' -Encoding UTF8 -Value $content
```

При работе с путями использовать `-LiteralPath`, если в имени есть кириллица,
пробелы, скобки, спецсимволы или символы вроде `[` и `]`.

## Python-скрипты в проектах F-Engineering

Если агент пишет вспомогательный Python для парсинга PDF/XLSX/CSV/HTML, скрипт
должен быть пригоден для повторного использования и безопасен для кириллицы.

Минимальные правила:

- сохранять `.py` как UTF-8;
- не вставлять кириллические пути внутрь stdin/heredoc-скрипта, если кодировка
  консоли не проверена;
- передавать сложные пути через аргументы CLI или переменные окружения;
- в Python использовать `Path` и явные кодировки;
- для текстового вывода включать UTF-8, если доступно:

```python
import sys

if hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8")
```

- для JSON писать `ensure_ascii=False`;
- для CSV, который будет открываться в Excel, использовать `utf-8-sig`;
- не оставлять полезный одноразовый скрипт только в папке проекта, если он
  решает повторяемую задачу. Его нужно обобщить, удалить клиентские данные и
  вынести в `tools/` базы знаний.

Пример безопасного чтения/записи:

```python
from pathlib import Path
import json

source = Path(input_path)
text = source.read_text(encoding="utf-8")
output.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")
```

## Генерация HTML, XLSX, DOCX и других выходных документов

Это обязательное правило для всех документных артефактов F-Engineering.

Если в результате есть русский текст, агент не должен генерировать финальный
HTML, XLSX, DOCX, Markdown, JSON или CSV через PowerShell heredoc/stdin-pipe
вида `@' ... '@ | python -`, если внутри скрипта есть русские строки,
кириллические пути или русское содержимое документа.

### Разрешенный маршрут

1. Создать или обновить отдельный `.py`, `.js` или другой генератор как
   UTF-8-файл с латинским именем, например:

   ```text
   scripts/generate_report_utf8.py
   ```

2. В генераторе хранить русский текст обычной Unicode-строкой, а файлы
   записывать явно как UTF-8.
3. Запускать генератор как файл:

   ```powershell
   $env:PYTHONUTF8 = '1'
   $env:PYTHONIOENCODING = 'utf-8'
   python scripts/generate_report_utf8.py
   ```

4. Рабочую проектную папку с кириллицей передавать в генератор через `Path.cwd()`
   или переменную окружения, а не вписывать кириллический путь внутрь текста
   команды.
5. Для временных папок, изображений, assets, cache и промежуточных файлов
   использовать латинские имена (`sheet_06_cladding.jpg`, `assets_ssp_v03`).
   Русские названия оставлять внутри таблицы или HTML как содержательные
   подписи, но не использовать их как служебные имена, если это не требуется.

### Запрещенный маршрут

Запрещено создавать финальные документы так:

```powershell
@'
from pathlib import Path

html = "Русский текст отчета"
Path(r"H:\Общие диски\...\отчет.html").write_text(html, encoding="utf-8")
'@ | python -
```

Даже если в одном окружении это сработало, в другом Windows/PowerShell может
заменить кириллицу на `????`, и итоговый HTML/XLSX будет испорчен.

### Обязательная read-back проверка

После генерации каждого русского HTML/XLSX/Markdown/JSON/CSV агент обязан
прочитать результат обратно и проверить, что кириллица сохранилась.

Для HTML/Markdown/JSON/TXT:

```python
text = path.read_text(encoding="utf-8")
assert "Москино" in text or "Фасад" in text
assert "????" not in text
```

Для XLSX:

```python
from openpyxl import load_workbook

wb = load_workbook(path, read_only=True, data_only=True)
sample = wb["Facade zones"]["B1"].value
assert sample == "Фасад / зона"
```

Проверка должна выполняться из той же проектной папки через `Path.cwd()` или
через переменную окружения, без кириллического литерала пути внутри stdin-pipe.

Если проверка показывает `????`, `Рџ`, `Ð`, `â` или русский текст не найден,
нельзя отдавать файл пользователю. Нужно пересобрать документ через UTF-8
генератор-файл или, если среда продолжает ломать Unicode, временно писать
русский текст транслитом латинскими буквами и явно сообщить об этом.

## Единый маршрут для Windows, PDF и кириллических путей

Если задача содержит кириллические пути, русские имена PDF/DWG/XLSX/DOCX,
русский текст или работу через PowerShell на Windows, агент не должен
перебирать способы чтения случайным образом.

Сначала применять единый маршрут:

1. В PowerShell получить абсолютный путь через `Resolve-Path -LiteralPath`.
2. Передать путь в Python или другой инструмент через переменную окружения, а
   не вписывать кириллический путь внутрь heredoc/stdin-скрипта.
3. Включить UTF-8 для вывода:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
[Console]::OutputEncoding = [Text.UTF8Encoding]::UTF8
```

4. В Python читать путь из `os.environ`:

```python
from pathlib import Path
import os

source = Path(os.environ["SOURCE_PDF"])
```

5. Выходные технические файлы, временные PNG/JPG/JSON/CSV можно размещать в
   ASCII-пути, например `C:\tmp\...`, но внутри результата сохранять исходные
   русские имена файлов как метаданные.
6. После чтения или записи выполнить короткую smoke-проверку кириллицы:
   убедиться, что в тексте нет неожиданных `????`, `Рџ`, `Рґ`, `СЃ`, `Ð`,
   `â`, кроме случаев, где они специально приведены как пример ошибки.

### Почему так

Нельзя передавать кириллический путь в Python через текст скрипта, который
подаётся в stdin, если консольная кодировка не гарантирована. В такой ситуации
путь может превратиться в `????`, и инструмент начнёт искать несуществующий
файл.

Правильная схема:

```powershell
$env:SOURCE_PDF = (Resolve-Path -LiteralPath 'C:\...\Русский файл.pdf').Path
$env:PYTHONIOENCODING = 'utf-8'
@'
import os
from pathlib import Path

pdf = Path(os.environ["SOURCE_PDF"])
print(pdf)
print(pdf.exists())
'@ | python -
```

Неправильная схема:

```powershell
@'
from pathlib import Path
pdf = Path(r'C:\...\Русский файл.pdf')
'@ | python -
```

Вторая схема допустима только если уже доказано, что канал передачи скрипта
сохраняет Unicode. По умолчанию в проектах F-Engineering её не использовать.

### Полевой симптом: `????` вместо пути

Если Python выводит путь вида `H:\????? ?????\...` или падает с
`FileNotFoundError` по пути, где русские части заменены на `????`, агент обязан
считать это ошибкой передачи Unicode, а не отсутствием файла.

Правильная реакция:

1. Не делать вывод, что исходный файл потерян или недоступен.
2. Не повторять тот же heredoc/stdin-подход с тем же кириллическим литералом.
3. Проверить файл в PowerShell через `Test-Path -LiteralPath` или `Get-Item -LiteralPath`.
4. Передать путь в Python через переменную окружения:

```powershell
$env:DOC_BASE = (Resolve-Path -LiteralPath 'H:\Общие диски\022-F_engineering\Папка проекта').Path
$env:PYTHONIOENCODING = 'utf-8'
@'
import os
from pathlib import Path

base = Path(os.environ["DOC_BASE"])
print(base)
print(base.exists())
'@ | python -
```

5. Если нужно передать несколько путей, использовать несколько переменных
   окружения (`SOURCE_XLSX`, `SOURCE_DOCX`, `OUTPUT_DIR`) или записать список
   путей во временный UTF-8 JSON-файл в ASCII-папке, например `C:\tmp`.

Это правило особенно важно для задач с Google Drive / общими дисками, где путь
содержит кириллицу, пробелы и длинные имена папок.

## Google Drive, общие диски и локальные зеркала GitHub

Локальное зеркало репозитория на Google Drive или общем диске — это удобная
рабочая копия, но не абсолютный источник истины.

Если `git`, `rg`, PowerShell или другой локальный инструмент показывает
`Permission denied`, частично читает файлы, не видит `.git` или отображает
русский Markdown как mojibake:

1. не считать файл испорченным;
2. не делать правки на основе битого вывода;
3. перечитать файл через GitHub connector или raw GitHub как UTF-8;
4. если нужно сравнить локальное зеркало с GitHub, проверять не только текст в
   консоли, но и SHA/размер/дату изменения;
5. для критичных правил считать GitHub `main` или рабочую ветку PR источником
   истины, а зеркало — кэшем для удобства агента.

При наличии двух Google-аккаунтов и разных букв дисков (`G:`, `H:`) агент обязан
фиксировать, из какого пути читает и куда пишет. Нельзя молча переносить
артефакты между личным и корпоративным диском, если пользователь указал рабочую
папку.

## PDF и рендер листов с кириллицей

Для PDF с русскими именами файлов:

1. Сначала проверить доступ к файлу через PowerShell:

```powershell
Test-Path -LiteralPath '<русский путь>'
Get-Item -LiteralPath '<русский путь>'
```

2. Для текстового слоя использовать Python-библиотеки (`pypdf`,
   `pdfplumber`) с путём из переменной окружения.
3. Для рендера через Poppler передавать путь как аргумент PowerShell-переменной,
   полученной через `Resolve-Path -LiteralPath`.
4. Если wrapper-команда `pdftoppm.cmd` не работает, проверить реальный
   исполняемый файл Poppler и вызвать его напрямую.
5. Рендерить страницы во временную папку с ASCII-путём, например:

```text
C:\tmp\<project_slug>\page-01.png
```

6. В отчёте указывать исходное русское имя PDF, номер страницы и назначение
   листа. Не переименовывать исходный PDF в латиницу только ради удобства.

## Запись HTML, Markdown, JSON и CSV

Для HTML с русским текстом:

- всегда добавлять `<meta charset="utf-8">`;
- записывать файл как UTF-8;
- если файл будут открывать двойным кликом в Windows/Chrome/Edge, допустимо
  использовать UTF-8 BOM для снижения риска неправильного определения
  кодировки.

Для PowerShell-записи HTML:

```powershell
$enc = [System.Text.UTF8Encoding]::new($true)
[System.IO.File]::WriteAllText($path, $html, $enc)
```

Для JSON:

```python
path.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")
```

Для CSV, который может открываться в Excel:

- использовать `utf-8-sig`, если файл предназначен для ручного открытия в
  Excel;
- использовать обычный `utf-8`, если CSV является только машинным промежуточным
  файлом.

## GitHub connector и git

- Файлы правил в GitHub хранить как UTF-8 Markdown.
- Через GitHub connector создавать и обновлять русские Markdown-файлы только как
  UTF-8 text content.
- Не коммитить файл, если перед коммитом русский текст выглядит битым.
- Перед push/PR проверять хотя бы один локальный или connector-readback просмотр
  измененных русских файлов.
- Не исправлять mojibake вручную заменами символов, если можно перечитать
  исходник в правильной кодировке.

## HTML, CSV, JSON и Markdown

Для HTML всегда указывать:

```html
<meta charset="utf-8">
```

Для CSV и JSON считать рабочей кодировкой UTF-8. Если файл открывается в Excel
или другой программе с битой кириллицей, не менять данные наугад: сначала
уточнить требуемую кодировку экспорта и сохранить отдельную версию, не портя
исходник.

Для Markdown не вставлять в документ строки, полученные из битого вывода
консоли. Сначала перечитать источник корректно.

## Запрещено

- Анализировать содержательно текст, который отображается как mojibake.
- Переписывать нормальный русский файл содержимым из битого консольного вывода.
- Делать вывод, что файл испорчен, пока не проверена кодировка чтения.
- Делать вывод, что файл отсутствует, если Python получил путь с `????`; сначала
  проверить Unicode-передачу пути и `Test-Path -LiteralPath` в PowerShell.
- Переименовывать русские файлы и папки в латиницу только ради удобства агента.
- Использовать ad hoc замену символов вместо корректного чтения источника.
- Оставлять повторяемые Python-инструменты только в папке разового проекта, если
  они уже доказали пользу для типовых задач F-Engineering.

## Мини-проверка перед завершением задачи

Если в задаче были русские файлы, перед финальным ответом проверить:

1. созданные или измененные файлы читаются как нормальная кириллица;
2. HTML содержит `meta charset="utf-8"`;
3. в выводе и файлах нет фрагментов `Рџ`, `Рґ`, `СЃ`, `вЂ`, `â`, `Ð`, если они не
   приведены специально как пример ошибки;
4. исходные русские имена файлов и папок сохранены без самовольного
   переименования;
5. если использовались Python/PowerShell/PDF-инструменты, кириллические пути
   передавались через `Resolve-Path -LiteralPath` и переменные окружения либо
   другим заранее проверенным Unicode-безопасным способом;
6. если использовалось локальное зеркало GitHub на Google Drive, результат
   проверен через GitHub connector или другой UTF-8 источник истины.

## Когда применять

Всегда при работе с русским языком, кириллицей, Windows/PowerShell, общими
дисками, Google Drive placeholder-файлами, GitHub Markdown и документными
артефактами F-Engineering.

# Эталон аналитического HTML-отчета

Статус: `Reference`

Этот файл заменяет прежний HTML-эталон и фиксирует reusable-структуру
аналитического отчета без хранения готового проектного HTML-документа в базе
знаний.

## Назначение

Использовать для аналитических записок, исследований, классификаторов,
нормативных обзоров, технических отчетов и других длинных содержательных
документов, которые затем могут быть сверстаны в HTML.

## Каркас документа

```text
Титульный блок
→ Содержание
→ Краткое резюме
→ Аналитические разделы
→ Таблицы и матрицы
→ Проверочные блоки
→ Выводы и следующие действия
```

## Титульный блок

Содержит:

- eyebrow: проект и тип документа;
- H1: название аналитического отчета;
- краткий подзаголовок с предметом анализа;
- метаданные: проект, дата, версия, статус.

Визуальное ядро титульного блока описано в
`document-standards/HTML_Analytical_Report_Style.md`.

## Содержание

Для длинных HTML-документов использовать интерактивное содержание.
В Markdown-эталоне фиксируется иерархия:

- разделы уровня H2;
- подразделы уровня H3;
- якоря или ссылки на разделы при HTML-реализации.

## Краткое резюме

Резюме должно содержать 3-7 ключевых выводов или решений.

Формат:

| N | Вывод / решение | Значение для проекта |
|---|---|---|
| 1 | Формулировка | Практическое значение |

## Аналитические разделы

Каждый раздел должен отвечать на отдельный управленческий или технический
вопрос. Не смешивать в одном разделе:

- исходные данные;
- метод анализа;
- вывод;
- открытые вопросы;
- финансовые последствия.

Если нужны все четыре элемента, оформлять их отдельными подразделами.

## Таблицы и матрицы

Таблицы использовать для сопоставлений, статусов, классификаторов, рисков,
источников и решений.

Базовый формат:

| Параметр | Значение | Источник / статус | Комментарий |
|---|---|---|---|
| Параметр | Значение | Источник | Комментарий |

Для HTML-реализации широкие таблицы должны быть адаптивными по правилам
`document-standards/HTML_Mobile_Standard.md`.

## Проверочные блоки

Если отчет содержит извлеченные данные, расчеты, объемы, классификацию по
источникам или проверяемые выводы, рядом с соответствующим разделом нужен
проверочный блок.

Формат Markdown:

```text
Проверочный блок
- Источник: файл / URL / документ
- Страница или лист: номер
- Что проверяется: категория данных
- Статус: подтверждено / требует проверки / расчетное допущение
```

Для HTML-реализации допускается раскрываемый блок `details`, но сам HTML-файл
не хранится в базе знаний как эталон.

## Выводы и следующие действия

Финальный раздел должен содержать:

- принятые решения;
- открытые вопросы;
- риски;
- следующие действия;
- ответственных или статус назначения ответственного.

## Обязательные правила применения

1. Сохранять деловой характер, спокойную визуальную систему и ясную иерархию.
2. Не хранить в базе знаний проектный HTML-отчет как шаблон.
3. Если проектный отчет породил полезный паттерн, переносить в базу только обезличенное Markdown-правило.
4. Для HTML-реализации соблюдать профильный стиль и мобильный стандарт.
5. Проверочные материалы держать в проектной папке или в составе проектного результата, а не в репозитории правил.

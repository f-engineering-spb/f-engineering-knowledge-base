# Google financial tools: таблицы, формы, двойная запись

Статус: `Candidate`

## Назначение

Методика описывает, как проектировать Google Sheets + Apps Script системы для учета движения денежных средств, когда пользователи вводят операции через личные листы или веб-форму, а система ведет общий журнал, остатки и двойную запись.

Документ возник из пилотного кейса учета платежей между участниками с кошельками `F1`, `F2K`, `F2`, внешними поступлениями, расходами и исправлением ошибочных операций.

## Область применения

Применять для задач, где нужны:

- общий журнал финансовых операций;
- личные листы участников;
- сводные остатки по участникам и формам средств;
- ввод из Google Sheets и/или мобильной веб-формы;
- контроль дублей;
- исправление ранее проведенных операций;
- двойная запись только для операций между участниками.

Не применять автоматически для бухгалтерского учета, налоговой отчетности и юридически значимых регистров без отдельной проверки специалистом.

## Базовая модель данных

Минимальный журнал операции должен содержать:

| Поле | Назначение |
|---|---|
| Дата | дата операции |
| Сумма | сумма операции |
| Операция | `Приход`, `Расход`, `Трансфер` |
| Счет | форма средств, например `F1`, `F2K`, `F2` |
| Откуда | участник или внешний объект |
| Куда | участник или внешний объект |
| Назначение | статья или назначение операции |
| Примечание | свободный комментарий |
| ID | технический идентификатор операции |
| Автор | участник, создавший запись |
| Статус | состояние записи |
| Создано | техническое время создания |

Правило: пользовательские поля должны быть простыми и короткими; технические поля скрываются или находятся в отдельной базе.

## Листы книги

Рекомендуемая структура книги:

| Лист | Назначение | Кто редактирует |
|---|---|---|
| `Журнал` | видимый общий журнал операций | только скрипт / администратор |
| `Операции_DB` | скрытая техническая база операций | только скрипт |
| `Сводная` | остатки по участникам и счетам | формулы или скрипт |
| `Справочники` | участники, объекты, назначения, счета | администратор |
| `Начальные остатки` | стартовые остатки на дату запуска | администратор |
| личные листы участников | блок ввода и список операций участника | участник в своем листе |
| `Диагностика` | время операций и ошибки | скрипт |

## Правила двойной записи

1. Двойная запись создается только когда операция затрагивает двух участников.
2. Если деньги пришли от внешнего объекта участнику, в личном листе отражается только запись участника; у объекта отдельный лист не создается.
3. Если деньги ушли от участника внешнему объекту, зеркальная запись не создается.
4. `Трансфер` означает перемещение между собственными счетами одного участника, а не передачу другому участнику.
5. Передача между участниками отражается как `Расход` у отправителя и `Приход` у получателя, но в технической базе должна иметь один общий ID операции.
6. В общем журнале желательно показывать одну бизнес-операцию, если пользователю не нужен отдельный вид дебета и кредита.

## Правила маршрутов средств

Если формы средств имеют жесткие маршруты, они должны быть явно описаны и проверяться скриптом.

Пример правил:

- `F1 -> F2K -> F2` разрешено;
- обратный путь запрещен;
- `F2` не конвертируется в `F2K`;
- `F2K` не конвертируется в `F1`;
- приход извне может быть `F1` или `F2`, если это задано бизнес-правилами;
- `F2K` как внешний приход запрещается, если это задано бизнес-правилами.

## Начальные остатки

Нельзя запускать финансовую таблицу без отдельного сценария начального состояния.

Перед вводом операций нужно определить:

1. дату начальных остатков;
2. список участников;
3. остатки по каждому счету каждого участника;
4. кто имеет право менять стартовые остатки;
5. как отличить стартовые остатки от обычных операций.

Рекомендуется отдельный лист `Начальные остатки`, где каждая строка содержит дату, участника и остатки по счетам. Операционные остатки считаются как начальный остаток плюс проведенные операции после даты запуска.

## Исправление операций

Исправление должно быть отдельной функцией, а не ручным изменением строк журнала.

Правильный сценарий:

1. пользователь выбирает операцию в личном листе;
2. операция загружается в блок ввода;
3. пользователь меняет сумму, счет, стороны, назначение или примечание;
4. нажимает `Исправить операцию`;
5. скрипт находит исходный ID;
6. заменяет запись в технической базе;
7. перестраивает только затронутые видимые листы;
8. записывает событие в историю изменений или диагностику.

Удаление операции лучше не делать обычной пользовательской кнопкой. Если операция была введена ошибочно, предпочтительнее исправить ее на правильную. Отмена нужна только как админская функция с историей.

## Защита от дублей

Защита от дублей нужна для новых операций, но не должна блокировать осознанное исправление.

Рекомендуемое правило:

- новая операция проверяется на дубль по дате, сумме, операции, счету, сторонам и назначению;
- проверка ограничивается разумным периодом, например текущим днем или ближайшими днями;
- исправление операции может привести запись к значениям, похожим на другую операцию, если пользователь сознательно исправляет уже существующую запись;
- при конфликте лучше показать понятное сообщение, а не молча игнорировать действие.

## Триггеры и кнопки в Google Sheets

### Что проверено в пилоте

Чекбоксы как кнопки работают быстро, но имеют UX-риск: если пользователь редактирует сумму и курсор остается внутри ячейки, Google Sheets может не зафиксировать новое значение до клика по другой ячейке. В результате первое нажатие на чекбокс может не выполнить ожидаемую команду.

### Рекомендация

Для пользовательских команд в личном листе использовать псевдокнопки в объединенных ячейках и `onSelectionChange`, а не чекбоксы, если важна простота для пользователя.

Рекомендуемый интерфейс:

- строка ввода операции;
- крупная ячейка `ПРОВЕСТИ НОВУЮ ОПЕРАЦИЮ`;
- крупная ячейка `ИСПРАВИТЬ ОПЕРАЦИЮ`;
- ниже список `Мои операции`.

При клике по псевдокнопке Google Sheets обычно завершает ввод в активной ячейке и затем вызывает обработчик выбора. Это надежнее для исправления суммы.

### Откат

Если тестируется новый механизм кнопок, оставить в коде возможность вернуться к чекбоксам через админское меню. Экспериментальный интерфейс должен быть обратимым.

## Производительность

Типичные узкие места:

- вставка строк сверху в журнал и личные листы;
- полная перестройка всех листов участников;
- формулы, пересчитывающие большие диапазоны;
- повторное чтение справочников и всей базы;
- лишние `SpreadsheetApp.flush()`.

Рекомендации:

1. Хранить операции в скрытом `Операции_DB`.
2. Видимые листы считать представлениями, а не первичным источником данных.
3. При новой операции обновлять только журнал и личные листы затронутых участников.
4. При исправлении перестраивать только листы участников, участвовавших в старой и новой версии операции.
5. Вести лист `Диагностика` с этапами: проверка, DB, журнал, личные листы, очистка.
6. Не оптимизировать вслепую: сначала замерять время этапов.

## Веб-форма для телефона

Веб-форма Apps Script должна использовать те же бизнес-функции, что и Google Sheets, но не зависеть от строк, кнопок и чекбоксов в таблице.

Требования:

- персональная ссылка участника с токеном;
- выбор операции, счета, сторон и назначения из справочников;
- ручной ввод суммы и примечания;
- режим `Новая операция`;
- режим `Мои операции`;
- режим `Исправление`;
- после успешной записи форма очищается и заново получает актуальные остатки и операции.

Если меняется интерфейс листа, веб-форма не должна ломаться. Для этого формы должны вызывать функции уровня данных, например `writeOperation_`, `replaceOperationRows_`, `rebuildPersonalSheets_`, а не имитировать действия пользователя в листе.

## Права доступа

Минимальные правила:

- общий журнал и база операций закрыты от обычного ручного редактирования;
- участник редактирует только свой лист или вводит данные через форму;
- справочники и начальные остатки редактирует администратор;
- скрипт проверяет, что пользователь исправляет только операцию, в которой участвует;
- токены веб-форм не публикуются в GitHub.

## Диагностика и эксплуатация

Обязательные диагностические записи:

| Поле | Назначение |
|---|---|
| Время | дата и время события |
| Действие | новая операция, исправление, веб-форма, ошибка |
| Участник | номер или код участника |
| Итого, сек | общее время |
| Этапы | время по этапам |
| Версия | версия кода |

Каждый релиз Apps Script должен менять строку версии диагностики, чтобы по таблице было видно, какой код реально отработал.

## Порядок разработки

1. Сначала описать ТЗ: участники, счета, операции, маршруты, права, начальные остатки, отчеты.
2. Нарисовать блок-схему движения средств.
3. Согласовать минимальный журнал операций.
4. Сделать пустой прототип таблицы.
5. Добавить начальные остатки до тестов.
6. Реализовать новую операцию.
7. Реализовать исправление операции.
8. Проверить двойную запись между участниками.
9. Проверить внешние приходы и расходы без зеркальных записей.
10. Добавить диагностику времени и ошибок.
11. Добавить мобильную веб-форму.
12. Проверить, что веб-форма и лист используют одну бизнес-логику.
13. Только после пилота переносить пакет в рабочую папку.

## Критерии готовности

Систему можно считать готовой к пилоту, если:

- новая операция проводится из листа;
- новая операция проводится из веб-формы;
- исправление работает из листа;
- исправление работает из веб-формы;
- двойная запись появляется только между участниками;
- внешние приходы и расходы не создают лишних зеркальных строк;
- начальные остатки учитываются в сводной;
- личные листы и журнал согласованы;
- диагностика показывает версию и время выполнения;
- есть понятный способ отката экспериментального интерфейса.

## Ограничения

- Не хранить в репозитории рабочие таблицы, финансовые данные, токены и ссылки с доступом.
- Не считать Google Sheets полноценной бухгалтерской системой без отдельной проверки.
- Не полагаться на ручное исправление строк как на основной механизм корректировок.
- Не смешивать пользовательский журнал и техническую базу в одном видимом листе, если есть двойная запись и исправления.

# F-Engineering Launcher

Статус: `Candidate`  
ID: `PRD-001`

## Назначение

F-Engineering Launcher — локальная диалоговая оболочка для выбора, запуска и
наблюдения за повторяемыми бизнес-модулями компании.

Лаунчер связывает привычную папку проекта, диалог с пользователем, реестр
доступных модулей, ход выполнения и созданные результаты. Пользователь не
обязан знать внутренние названия скриптов, агентов или сервисов.

## Граница продукта

Лаунчер отвечает за:

- прием корневой папки проекта через drag-and-drop или системный выбор папки;
- отображение реального дерева файлов и подпапок;
- краткий снимок состава входных данных;
- выбор подразделения и модуля;
- свободную постановку задачи через пункт `Иное`;
- проверку обязательных параметров и прав;
- запуск модуля;
- показ этапа, процента, текущего файла и журнала;
- регистрацию и повторное открытие результатов.

Лаунчер не отвечает за предметную логику конкретного модуля. Каждая
повторяемая обработка оформляется отдельным бизнес-модулем со своим входом,
выходом, правилами, проверками и критериями готовности.

## Архитектурная схема

```text
Папка проекта
    -> сканер структуры
    -> паспорт рабочей сессии
    -> диалоговый маршрутизатор
    -> реестр подразделений и модулей
    -> исполнитель выбранного модуля
    -> каталог результатов
    -> дерево проекта и карточка результата
```

## Базовый пользовательский сценарий

1. Пользователь выбирает или перетаскивает корневую папку проекта.
2. Лаунчер быстро строит дерево и считает форматы файлов.
3. Лаунчер показывает нумерованный список подразделений без автоматической
   рекомендации.
4. Пользователь выбирает подразделение.
5. Лаунчер показывает доступные модули.
6. Пользователь выбирает модуль либо пункт `Иное`.
7. Для готового модуля лаунчер показывает карточку запуска.
8. После запуска пользователь видит этап, процент, текущий файл и журнал.
9. Созданный результат появляется в дереве и в карточке результата.
10. Пользователь может вернуться к карточке, открыть основной результат или
    показать его расположение в Проводнике.

## Отношение к бизнес-модулям

Лаунчер является платформой оркестрации, а не монолитным бизнес-процессом.

Каждый новый модуль разрабатывается:

- в отдельной ветке;
- в отдельной папке `business-processes/modules/`;
- по `business-processes/MODULE_STANDARD.md`;
- с отдельной записью в реестре модулей;
- без клиентских исходников в GitHub.

Первый связанный модуль: `BPM-001` — первичная индексация, классификация и
визуальный навигатор входящей документации.

## Данные и безопасность

- Клиентские PDF, DWG, DOCX, XLSX и другие исходники в GitHub не переносятся.
- В репозитории хранятся только обезличенные контракты, правила, схемы и
  проверяемый исходный код.
- Локальные пути и проектные имена в примерах заменяются нейтральными
  обозначениями.
- Любое внешнее или разрушительное действие требует отдельного подтверждения.

## Визуальный стиль

Интерфейс лаунчера следует `DS-011`: тёмная машинная IDE-стилистика,
моноширинная типографика, сине-металлический основной акцент и семантические
цвета состояний.

Документы, реестры и отчёты, которые лаунчер создаёт для чтения, согласования
или отправки, следуют светлому документному стандарту `DS-010`.

## Критерии готовности платформы

- корневая папка принимается без изменения клиентских файлов;
- дерево соответствует реальной структуре на диске;
- подразделение и модуль можно выбрать без изучения отдельного интерфейса;
- отсутствующие обязательные данные блокируют запуск;
- каждый запуск фиксирует модуль, версию правил, статус и результат;
- ход долгой операции остается видимым;
- результат можно открыть и показать в его папке;
- дерево можно изменять по ширине и полностью сворачивать;
- окно поддерживает обычное масштабирование и полноэкранный режим;
- предметная логика не смешивается с кодом оболочки.

## Ветвление

- платформа лаунчера: `codex/rules-f-engineering-launcher`;
- каждый бизнес-модуль: отдельная ветка вида `codex/rules-<module-name>`;
- существенное изменение визуального стандарта: отдельная ветка вида
  `codex/style-<style-name>`.

После merge ветки платформа получает статус, указанный в реестре знаний.

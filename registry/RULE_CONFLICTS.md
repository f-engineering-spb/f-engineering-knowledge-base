# Реестр конфликтов правил

Статус: `Approved`

Файл фиксирует известные пересечения правил и порядок выбора приоритета.

## Общий порядок разрешения конфликтов

1. Если есть правило проектной папки `AGENTS.md`, оно уточняет общие правила для данного проекта.
2. Если методика работы требует один состав данных, а стиль документа другой способ оформления, методика определяет содержание, стиль определяет форму.
3. Если два стандарта оформления предлагают разные компоненты, сохранять неизменное ядро фирменного стиля и выбирать компонент, который лучше решает задачу.
4. Если правило имеет статус `Candidate`, оно не отменяет `Approved`.
5. Если пользователь прямо утвердил новый подход в задаче, оформить его как proposal и не считать глобальным правилом до обновления реестра.

## Известные пересечения

| Область | Возможный конфликт | Решение |
|---|---|---|
| HTML-таблицы на телефоне | обычный HTML-стандарт предлагает карточки, а расчетная спецификация требует единую таблицу | для расчетных спецификаций использовать единую таблицу с локальной прокруткой внутри контейнера |
| Фасадная отделка против фасадных конструкций | задача может звучать как отделка, но для КП нужны все фасадные конструкции | применять полный многоконтурный фасадный аудит и матрицу полноты |
| Проверочные материалы | отчет может ссылаться на внешние PDF/DWG, но пользователь хочет отправляемый HTML | для отправляемой версии встраивать ключевые превью и таблицы прямо в HTML |
| PDF против HTML | PDF удобен для печати, но плохо держит длинные проверочные блоки | основным рабочим форматом считать HTML, PDF делать как экспорт при необходимости |
| PPTX против HTML-презентации | PPTX удобен для редактирования слайдов, но хуже передает раскрываемые проверки | для доказательных презентаций использовать HTML; PPTX делать как дополнительную версию |
| Author values vs calculated values | авторская спецификация и CAD-расчет могут отличаться | маркировать статусы A/B/C/D, не смешивать без пояснения, расхождения более 2% выносить в контроль |
| Проектные материалы и GitHub | полезный кейс содержит клиентские данные | в GitHub переносить только обезличенное правило, исходники и клиентские файлы оставлять в проектной папке |
| Цветной/градиентный стиль против черно-белого минималистичного | старые или экспериментальные правила могут предлагать цветные блоки, градиенты или декоративную подачу | для новых коммерческих предложений, дорожных карт и управленческих документов по умолчанию применять `document-standards/Black_White_Minimalist_Document_Style.md`; цветной стиль использовать только по прямому указанию пользователя или при наличии утвержденного проектного шаблона |

## Что делать при новом конфликте

1. Зафиксировать конфликт в проектном отчете или decision log.
2. Не менять `main` напрямую.
3. Подготовить proposal с описанием конфликта и выбранного решения.
4. После проверки обновить этот файл.

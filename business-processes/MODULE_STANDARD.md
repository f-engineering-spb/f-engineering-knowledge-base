# Стандарт описания бизнес-модуля

Статус: `Candidate`

## Назначение

Этот стандарт задает единый формат для описания повторяемых бизнес-модулей
F-Engineering.

Бизнес-модуль - это самостоятельный кирпичик работы, который можно подключать к
разным процессам компании: тендеру, подготовке КП, старту проектирования,
производству, монтажу, закрытию объекта или архивному обращению к данным.

Модуль не должен быть слишком большим. Он должен решать одну понятную проблему,
иметь входные данные, выходные артефакты, пользователей, критерии готовности и
инструкцию оператору.

## Зачем нужен стандарт

Если каждый новый модуль описывать произвольно, база знаний быстро превратится в
склад разнородных заметок. Стандарт нужен, чтобы десятки будущих автоматизаций
можно было:

- сравнивать между собой;
- подключать к общей карте процессов;
- передавать новым сотрудникам;
- проверять по одинаковым критериям;
- развивать без переделки первых шагов.

## Обязательная карточка модуля

Каждый модуль должен содержать следующие поля.

| Поле | Что описывает |
|---|---|
| ID | Уникальный номер модуля, например `BPM-001` |
| Название | Краткое рабочее название |
| Статус | `Draft`, `Candidate`, `Approved`, `Deprecated` |
| Назначение | Что модуль делает и зачем нужен |
| Бизнес-проблема | Какая потеря времени, ошибка или повторяемая боль устраняется |
| Пользователи | Кто использует результат модуля |
| Где применяется | На каких стадиях процесса модуль полезен |
| Старт модуля | Какое событие запускает работу |
| Финиш модуля | Когда модуль считается завершенным |
| Входные данные | Какие файлы, ссылки, таблицы, папки или решения нужны на входе |
| Выходные артефакты | Что должно быть создано после выполнения |
| Последовательность работы | Пошаговая процедура |
| Данные и сущности | Какие признаки, колонки, справочники или статусы создаются |
| Инструменты | Google Drive, Google Sheets, HTML, Apps Script, Codex, локальные скрипты и т.д. |
| Критерии готовности | Как понять, что модуль выполнен качественно |
| Ограничения | Что модуль не делает и где его нельзя применять без доработки |
| Что нельзя хранить в GitHub | Клиентские файлы, чертежи, цены, КП поставщиков, конфиденциальные данные |
| Связанные модули | Какие модули идут до, после или параллельно |

## Минимальная структура папки модуля

```text
business-processes/modules/<module-slug>/
  README.md
  operator-instruction.md
  data-model.md
  implementation-notes.md
```

Если модуль становится основой для регулярной работы, можно добавить:

```text
  prompts.md
  viewer-requirements.md
  quality-checklist.md
  examples.md
```

## Статусы

| Статус | Значение |
|---|---|
| `Draft` | Черновик, идея еще не проверена на рабочем кейсе |
| `Candidate` | Модуль уже описан и опробован, но требует практической проверки или уточнений |
| `Approved` | Модуль принят как действующее правило после проверки и merge в `main` |
| `Deprecated` | Модуль устарел, заменен другим или оставлен только для истории |

## Правило самостоятельности

Модуль должен быть полезен сам по себе.

Если модуль нельзя выполнить без знания всей будущей большой схемы, он слишком
крупный или плохо отделен. Его нужно разделить на несколько меньших модулей.

Хорошая проверка:

```text
Можно ли дать этот модуль оператору как отдельную инструкцию и получить
полезный результат без построения всей системы компании?
```

Если ответ да, модуль подходит для реестра.

## Правило подключения к процессам

Один и тот же модуль может применяться в нескольких местах.

Например, модуль первичной индексации входящей документации может использоваться:

1. на старте тендера;
2. на старте проектирования;
3. позднее как справочный архив входящих данных.

Поэтому модуль не должен жестко называться только тендерным или только
проектным. В `PROCESS_MAP.md` фиксируется, где он применяется.

## Контрольные вопросы перед добавлением нового модуля

Перед добавлением нового модуля ответить на вопросы:

1. Какую повторяемую боль он снимает?
2. Кто пользователь результата?
3. Когда модуль начинается?
4. Когда модуль заканчивается?
5. Какие данные нужны на входе?
6. Какие артефакты получаются на выходе?
7. Как проверить, что модуль выполнен?
8. Можно ли применить модуль на другом объекте?
9. Какие данные нельзя переносить в GitHub?
10. К каким стадиям процесса он может быть подключен?

Если на эти вопросы нельзя ответить, модуль пока не готов для реестра.

## Правило GitHub

GitHub хранит метод, структуру, правила, инструкции, шаблоны и критерии качества.

GitHub не хранит клиентские документы, проектные чертежи, коммерческие цены,
закупочные предложения, конфиденциальные расчеты и рабочие исходники объектов.

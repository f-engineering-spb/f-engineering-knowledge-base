# Инструкция оператору: первичная индексация входящей документации

Статус: `Candidate`

## Цель

Создать поисковый реестр и, при необходимости, визуальный просмотрщик входящей
документации проекта.

Оператор должен пройти путь:

```text
входящая папка -> сырой реестр -> сущности проекта -> классификация строк -> фильтры -> просмотрщик
```

Главный результат: пользователи перестают искать файлы вручную по папкам и
получают одну понятную точку входа.

## Роли пользователей

Перед началом оператор должен понять, кто будет пользоваться результатом:

- коммерсанты на стадии КП;
- проектировщики на старте проектирования;
- руководители проектов;
- участок или производство;
- технические специалисты.

От этого зависит, какие сущности и фильтры действительно нужны.

## Шаг 1. Подготовить исходную папку

1. Подтвердить активную проектную папку.
2. Подтвердить, где она находится: локально, в Google Drive, на общем диске или
   одновременно в нескольких местах.
3. Не переименовывать и не перемещать клиентские файлы до первого сканирования.
4. Зафиксировать локальный путь и облачную ссылку на папку.
5. Зафиксировать дату получения пакета документации.

Важно: на этом этапе оператор не оценивает качество документации и не решает,
что важно. Сначала нужно получить карту входящего хаоса.

## Шаг 2. Собрать сырой реестр

Собрать все файлы в таблицу.

Минимально указать:

- имя файла;
- расширение;
- путь к папке;
- родительскую папку;
- ветку папок / источник;
- локальный путь;
- Google Drive URL или ID, если доступен;
- размер файла, если доступен;
- дату изменения, если доступна.

На этом шаге не решать, что важно. Сначала нужно увидеть, что вообще есть.

## Шаг 3. Просмотреть сырой реестр

Изучить названия папок и файлов. Понять естественную структуру объекта.

Вопросы для проверки:

- Есть ли корпуса или секции?
- Разделены ли планы, фасады, разрезы, узлы, спецификации?
- Есть ли пары PDF и DWG?
- Есть ли архивы или дубли?
- Какие файлы нужны коммерсантам для оценки?
- Какие файлы нужны проектировщикам на старте?
- Какие файлы могут пригодиться руководителям проектов и участку как визуальная
  основа?
- Какие файлы являются фоном или административными материалами?

Результат шага: оператор понимает, какие признаки реально видны в документации.

## Шаг 4. Определить сущности

Создать только те колонки сущностей, которые нужны проекту.

Стартовый набор:

- тип документа;
- формат;
- источник / ветка папок;
- статус.

Часто добавляются:

- корпус;
- секция;
- фасад;
- ось / отметка;
- раздел;
- стадия;
- версия / ревизия;
- вид работ;
- комментарий.

Добавлять новые сущности только тогда, когда они действительно нужны для поиска
или фильтрации.

Правило: сущности не навязываются всем проектам одинаково. На простом объекте их
может быть 5, на сложном - 20 и больше.

## Шаг 5. Классифицировать строки

Применить правила по имени файла и пути. Затем вручную проверить неясные файлы.

Примеры:

- имя содержит `facade` или `фасад` -> `document_type = facade`;
- имя содержит `section` или `разрез` -> `document_type = section`;
- расширение `.dwg` -> `format = DWG`;
- папка содержит `archive` или `архив` -> `status = archive`.

Сомнительные строки помечать как `requires review`.

Не классифицировать молча файл, если оператор не уверен. Лучше честная пометка
для проверки, чем красивая ошибка в фильтре.

## Шаг 6. Согласовать набор фильтров

После классификации определить, какие фильтры нужны пользователю.

Фильтр создается только на основании сущности, которая уже есть в реестре.

Примеры фильтров:

- корпус;
- секция;
- тип документа;
- формат;
- раздел;
- статус;
- источник / папка;
- фасад / ось.

Если сущность не помогает пользователю найти файл, не превращать ее в фильтр.
Просмотрщик должен быть быстрее папок, а не сложнее папок.

## Шаг 7. Создать рабочее представление

Выбрать самый простой полезный результат:

- Google Sheets с фильтрами, если команде нужна только таблица;
- HTML-просмотрщик, если нужен быстрый визуальный просмотр PDF/DWG;
- Apps Script Web App, если просмотрщик должен открываться из облачного Google
  Drive;
- локальный launcher, если DWG должны открываться на рабочем компьютере.

Если создается HTML или Apps Script просмотрщик, использовать актуальный
визуальный стандарт:

`docs/F_ENGINEERING_VISUAL_STYLE.md`

## Шаг 8. Опубликовать точку входа

Разместить ссылку на реестр или просмотрщик в проектной рабочей папке.

Рекомендуемые точки входа:

- Google Doc со ссылкой в папке проекта;
- закрепленная Google Sheet;
- Apps Script Web App URL;
- локальный HTML-файл для рабочего компьютера.

Название точки входа должно быть понятным человеку, например:

```text
Входящая документация - реестр и просмотрщик
```

## Шаг 9. Проверить на пользователе

Попросить целевого пользователя найти несколько файлов:

- PDF фасада;
- PDF разреза;
- DWG-аналог;
- спецификацию или другой важный исходный документ;
- файл из спорной или глубокой папки.

Модуль успешен, если пользователь находит файлы через реестр или просмотрщик
быстрее, чем через папки.

## Шаг 10. Сохранить метод

В GitHub записываются повторяемые правила, но не клиентские файлы, проектные
чертежи, коммерческие цены, КП поставщиков и конфиденциальные расчеты.

После успешного применения модуля оператор может добавить в GitHub только:

- уточнение инструкции;
- новый шаблон сущностей;
- правило классификации;
- обезличенный пример;
- замечание о типовой ошибке;
- улучшение чек-листа.

## Минимальный отчет оператора

После выполнения модуля оператор готовит короткий отчет:

```text
1. Где лежала входящая документация.
2. Сколько файлов найдено.
3. Какие форматы обнаружены.
4. Какие сущности созданы.
5. Какие фильтры сделаны.
6. Где открыть реестр / просмотрщик.
7. Какие файлы требуют ручной проверки.
8. Какие ограничения есть у результата.
```

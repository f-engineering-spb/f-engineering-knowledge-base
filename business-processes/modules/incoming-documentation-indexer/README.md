# BPM-001. Первичная индексация входящей документации

Статус: `Candidate`

## Роль модуля

`BPM-001` - первый эталонный бизнес-модуль в библиотеке повторяемых механизмов
F-Engineering.

Он не является разовой автоматизацией и не привязан к одному объекту. Это
самостоятельный кирпичик, который можно подключать к разным стадиям: старту
тендера, подготовке коммерческого предложения, старту проектирования и
последующему обращению к входящим исходникам.

## Назначение

Модуль первичной индексации входящей документации предназначен для начальной
обработки документации заказчика.

Модуль превращает неструктурированное дерево папок в проверяемый реестр файлов
и, при необходимости, в визуальный навигатор документации. Он применяется, когда
команда получает много PDF, DWG, XLSX, DOCX, изображений или других файлов и
должна быстро понять, что внутри, не открывая папки вручную одну за другой.

## Бизнес-проблема

На старте тендера или проектирования коммерсанты, проектировщики и руководители
проектов часто тратят время не на анализ, а на поиск: где лежит фасад, где
разрез, где спецификация, где DWG, какая папка актуальна, что является архивом,
а что рабочим исходником.

Один и тот же комплект документов многократно открывают разные люди. Модуль
сокращает это время за счет единой точки входа: реестр + сущности + фильтры +
визуальный просмотр.

## Где применяется модуль

Модуль применяется на трех стадиях:

1. Старт тендера и коммерческого предложения.
2. Старт проектирования, когда проектировщики начинают разбирать исходники
   заказчика.
3. Последующее обращение к исходной документации, когда руководителю проекта,
   производству или участку нужно увидеть, что было передано заказчиком на
   старте.

Обычно модуль завершается после того, как входящая документация собрана в
реестр, классифицирована и опубликована как рабочая таблица или просмотрщик. При
получении нового пакета документов модуль можно обновлять.

## Пользователи

Основные пользователи:

- коммерсанты;
- проектировщики;
- руководители проектов;
- технические специалисты, готовящие состав работ;
- сотрудники участка, которым нужны исходные PDF-фасады как визуальная основа.

## Старт и финиш

### Старт

Модуль начинается, когда компания получает пакет входящей документации:

- папку Google Drive;
- локальную папку;
- архив;
- набор PDF / DWG / XLSX / DOCX / PNG / JPG;
- смешанную структуру папок от заказчика.

На старте не нужно знать все сущности. Сначала нужно увидеть, что вообще пришло.

### Финиш

Модуль считается завершенным, когда:

1. создан сырой реестр файлов;
2. определены сущности конкретного проекта;
3. строки реестра размечены этими сущностями;
4. создана рабочая точка входа: Google Sheet, HTML-просмотрщик, Apps Script Web
   App или другой согласованный интерфейс;
5. целевой пользователь может найти нужные файлы быстрее, чем через ручное
   перемещение по папкам.

## Последовательность работы

### 1. Собрать сырой реестр файлов

Сканируется входящая папка проекта и создается первичный список всех файлов.

Минимальные поля реестра:

- имя файла;
- расширение / формат;
- полный путь к файлу;
- родительская папка;
- ветка папок / источник;
- локальный путь, если доступен;
- ссылка Google Drive, если доступна;
- Google Drive file ID, если доступен;
- размер файла;
- дата изменения.

Цель: увидеть состав полученной документации без ручного перемещения по папкам.

### 2. Определить сущности проекта

После просмотра сырого реестра определяется, какие признаки важны именно для
этого объекта. Нельзя заставлять все проекты жить в одном наборе колонок.

Возможные сущности:

- объект / проект;
- корпус;
- секция;
- фасад / ось / отметка;
- тип документа;
- вид работ;
- раздел;
- стадия;
- пакет исходных данных;
- формат файла;
- версия / ревизия;
- статус;
- комментарий.

На простом объекте сущностей может быть 5, на сложном - 20 и больше.

### 3. Классифицировать файлы

Каждой строке реестра присваиваются значения сущностей.

Классификация может быть:

- автоматической, по имени файла и пути;
- правиловой, по принятому шаблону именования;
- ручной, если имена файлов неочевидны;
- смешанной: автомат предлагает, человек проверяет.

Неясные файлы нужно помечать как `requires review`, а не классифицировать
молча и предположительно.

### 4. Сформировать фильтры и просмотрщик

На основании утвержденных сущностей создаются фильтры, карточки и рабочие
представления.

Важно: фильтры не придумываются заранее. Они рождаются из сущностей конкретного
проекта. Если на объекте есть секции, создается фильтр по секциям. Если секций
нет, фильтр не нужен.

Возможные результаты:

- Google Sheets реестр с фильтрами;
- HTML-просмотрщик с карточками и предпросмотром файлов;
- Apps Script Web App для открытия из облачного Google Drive;
- отдельные представления для входящих чертежей, коммерции, проектирования или
  архива;
- простой список ссылок, если визуальный просмотр не нужен.

Для чертежей предпочтительный просмотрщик содержит:

- поиск;
- фильтры по сущностям;
- карточки файлов;
- предпросмотр PDF;
- ссылки Google Drive;
- опциональный локальный запуск DWG, если на компьютере подключен Google Drive
  for desktop и запущен локальный launcher.

## Рекомендуемая архитектура

Использовать двухслойный подход:

1. Реестр: Google Sheets или другая таблица хранит полный индекс файлов и
   классификацию.
2. Витрина: HTML / Apps Script показывает только те представления, которые
   нужны на конкретном объекте.

Так классификация остается проверяемой, а просмотрщик не перегружается лишними
фильтрами.

## Входные и выходные данные

Входные данные:

- входящая папка проекта;
- пакеты документов заказчика;
- структура папок;
- имена файлов;
- правила именования, если они есть;
- локальный путь подключенного диска, если используется.

Выходные данные:

- сырой реестр файлов;
- классифицированный реестр;
- перечень сущностей конкретного проекта;
- визуальный просмотрщик или рабочие фильтрованные представления;
- список нераспознанных файлов и дублей;
- комментарии оператора для улучшения правил.

## Критерии готовности

Модуль выполнен, если:

1. все видимые исходные файлы попали в реестр;
2. ключевые сущности проекта определены;
3. важные файлы классифицированы достаточно для фильтрации;
4. сомнительные файлы помечены для проверки;
5. целевой пользователь находит документы через реестр или просмотрщик быстрее,
   чем через папки;
6. ссылка на реестр или просмотрщик размещена в проектной рабочей папке;
7. клиентские файлы и конфиденциальные коммерческие данные не перенесены в
   GitHub.

## Ограничения

Модуль не заменяет:

- коммерческий расчет;
- проектирование;
- аудит чертежей;
- подсчет объемов;
- согласование документации;
- управление архивом проекта.

Он создает быструю точку входа в полученную или рабочую документацию.

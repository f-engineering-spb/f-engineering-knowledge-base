# GitHub workflow for the F-Engineering knowledge base

Статус: `Approved`

## Назначение

Этот документ объясняет, как сотрудникам F-Engineering пользоваться GitHub-базой
знаний, как добавлять новые правила после проектной работы и как понимать, что
уже есть в базе.

GitHub здесь используется не как архив файлов, а как контур утверждения знания:
что предложено, что проверено, что стало правилом, где есть конфликт и кто
принял решение.

## Что есть в базе знаний

База знаний состоит из нескольких типов материалов:

| Раздел | Что хранится | Как использовать |
|---|---|---|
| `agent-instructions/` | правила поведения агентов, работа с проектными папками, UTF-8, стиль общения | читать перед началом работы и при настройке нового чата |
| `governance/` | порядок управления знаниями, статусы, приоритеты | читать при добавлении или изменении правил |
| `registry/` | реестр знаний, карта применения, конфликты, ветки | использовать как оглавление и диспетчер правил |
| `methodologies/` | методики выполнения работ: аудит чертежей, фасадная спецификация, дорожные карты | применять по типу задачи |
| `document-standards/` | визуальные и структурные стандарты документов | применять при подготовке выдаваемого результата |
| `templates/` | стартовые структуры документов и отчетов | использовать как основу результата |
| `tools/` | повторяемые скрипты и утилиты | использовать для извлечения, проверки и расчётов |
| `proposals/` | предложения, пилотные или экспериментальные правила | применять только осознанно, пока не утверждены |
| `.github/` | GitHub-процесс: PR-шаблон, issue-шаблоны, CODEOWNERS, проверки | обеспечивает порядок пополнения базы |

Главное оглавление:

1. `START_HERE.md`
2. `AGENTS.md`
3. `registry/KNOWLEDGE_REGISTRY.md`
4. `registry/APPLICATION_MAP.md`
5. `registry/RULE_CONFLICTS.md`

## Как понять, что уже есть в базе

1. Открыть `registry/KNOWLEDGE_REGISTRY.md`.
2. Найти материал по типу:
   - `Core` - базовые правила;
   - `Workflow` - методика работы;
   - `Style` - стиль документа;
   - `Template` - шаблон;
   - `Tool` - инструмент.
3. Проверить статус:
   - `Approved` - применять по умолчанию;
   - `Review` - можно учитывать, но внимательно;
   - `Candidate` или `Pilot` - не считать глобальным правилом;
   - `Deprecated` или `Archived` - не применять.
4. Открыть `registry/APPLICATION_MAP.md` и найти строку по типу задачи.
5. Читать только те файлы, которые указаны для задачи. Не надо загружать всю базу
   знаний сразу.

## Когда проектный результат становится новым знанием

Новый результат стоит переносить в базу знаний, если он:

- повторяется или, вероятно, повторится в других проектах;
- объясняет, как решать типовую инженерную, сметную, документную или
  управленческую задачу;
- помогает избежать ошибки;
- задаёт проверяемый порядок действий;
- может быть обезличен и понятен без клиентских исходников.

Не переносить в GitHub:

- клиентские PDF, DWG, XLSX, DOCX;
- сметы, счета, договоры, фотографии, финансовые данные;
- персональные данные;
- внутренние коммерческие детали проекта;
- тяжёлые промежуточные файлы.

## Процесс добавления нового знания

1. Зафиксировать наблюдение в проектной папке.
2. Сформулировать универсальное правило без клиентских данных.
3. Проверить `registry/KNOWLEDGE_REGISTRY.md`: нет ли уже похожего правила.
4. Проверить `registry/APPLICATION_MAP.md`: куда новый материал должен
   подключаться.
5. Проверить `registry/RULE_CONFLICTS.md`: не конфликтует ли новое правило с
   уже утверждённым.
6. Создать issue `New reusable knowledge`, если мысль ещё не готова как файл.
7. Создать ветку от `main`.
8. Добавить или изменить материал.
9. Обновить реестр и карту применения.
10. Если есть конфликт, обновить `registry/RULE_CONFLICTS.md`.
11. Открыть Pull Request.
12. Заполнить PR-шаблон.
13. Дождаться автоматической проверки `Knowledge Base Checks`.
14. После review и исправлений выполнить merge в `main`.
15. Обновить локальные зеркала на общих дисках.

## Проверка конфликтности

Новый материал конфликтует с существующими правилами, если он:

- предлагает другой порядок действий для того же типа задачи;
- меняет статус источника истины;
- меняет приоритет между проектным `AGENTS.md`, методикой, стилем и шаблоном;
- требует другой формат результата;
- меняет правила безопасности, конфиденциальности или UTF-8;
- делает старое правило частично неверным.

Если конфликт найден:

1. не прятать его в тексте нового правила;
2. описать конфликт в Pull Request;
3. добавить строку в `registry/RULE_CONFLICTS.md`;
4. указать, какое правило имеет приоритет и почему;
5. если старое правило устарело, перевести его в `Deprecated` отдельным
   изменением реестра.

## Что происходит после пополнения

После merge в `main`:

1. новая версия становится источником утверждённого знания;
2. `KNOWLEDGE_REGISTRY.md` показывает, что материал существует и в каком он
   статусе;
3. `APPLICATION_MAP.md` показывает, когда его читать;
4. `RULE_CONFLICTS.md` фиксирует известные пересечения;
5. GitHub хранит историю: кто, когда и зачем изменил знание;
6. зеркала на общих дисках обновляются из `main`;
7. новые чаты и проектные работы должны читать обновлённую базу перед стартом.

## Роли GitHub в этой системе

| Функция GitHub | Для чего нужна в базе знаний |
|---|---|
| Repository | хранит всю структуру базы |
| Branch | позволяет безопасно готовить изменение |
| Commit | фиксирует одну логическую правку |
| Pull Request | обсуждает и проверяет изменение перед утверждением |
| Review comments | указывает спорные места прямо в строках |
| Issues | фиксирует идеи, конфликты и задачи развития |
| Actions | автоматически проверяет UTF-8, реестр и базовую целостность |
| CODEOWNERS | назначает ответственного за критичные разделы |
| Branch protection | не даёт ломать `main` без PR и проверок |

## Мини-инструкция для коллег

Если в проекте родилось новое правило:

1. Не кладите проектные файлы в GitHub.
2. Откройте issue `New reusable knowledge`.
3. Опишите, из какого проекта возникло знание и почему оно повторяемое.
4. Укажите, какие существующие правила могут пересекаться.
5. Подготовьте обезличенный Markdown-файл, шаблон или инструмент.
6. Обновите `KNOWLEDGE_REGISTRY.md`.
7. Обновите `APPLICATION_MAP.md`, если правило должно применяться в новых задачах.
8. Обновите `RULE_CONFLICTS.md`, если есть противоречие.
9. Откройте Pull Request.
10. Не просите merge, пока не прошла автоматическая проверка и не понятно, как
    новое правило будет применяться.

Короткая формула:

```text
Проектный опыт -> обезличенное правило -> проверка конфликтов -> PR -> проверка -> merge -> обновление зеркал.
```
